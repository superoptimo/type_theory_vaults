## Why the untyped calculus isn't enough

The pure (untyped) lambda-calculus can express any computable function, which is exactly the problem. Turing-completeness means there is no algorithm that looks at an untyped term and tells you, in general, whether it will diverge, or whether it will get stuck trying to apply a boolean like a function. `(λx.x) true` is fine; `true true` — applying a boolean to an argument — reduces to nothing at all under the evaluation rules. It's not an error the language catches; it's a term that simply has no next step and isn't a value either. Pierce calls this a **stuck term**, and it's the formal stand-in for "the program crashed."

Chapter 8 already built a type system for a boolean/number calculus with no binders at all — `Bool` and `Nat` — and used it to rule out stuck terms like `if 0 then 1 else 2` before running anything. Chapter 9's job is to do the same thing for the lambda-calculus's actual novel content: abstraction and application. The obvious first attempt is to invent one type, call it `→`, and give every abstraction that type:

$$
\frac{}{\lambda x.\,t : \to}
$$

**What breaks with this:** it type-checks `λx.true` and `λx.λy.y` identically, as "a function." But applying the first to `true` yields a `Bool`; applying the second yields another function. A single type `→` throws away exactly the information you need to check an application — what the function expects, and what it returns. So the type has to be parameterized by both: an infinite family $T_1 \to T_2$, one for each pair of "argument type, result type." That single move — types indexed by other types — is the entire content of function types, and it's also the thing that later chapters ([[Subtyping|subtyping]], polymorphism, kinds) keep re-doing at higher levels of the type hierarchy.

The cost of adding this type discipline is real, not just a bookkeeping tax: **some untyped terms become permanently untypeable.** Self-application `x x` is the sharpest example — no type $T$ lets you write $x : T$ and simultaneously $x : T \to T'$ for the same $x$ in the same context, because `T` would have to equal `T → T'`, an infinite/non-well-founded type that the grammar below doesn't generate. Self-application is exactly the mechanism the untyped Y-combinator used to build general recursion (Ch. 5) — so simply typed lambda-calculus, on its own, cannot express unrestricted recursion. That's not a bug pointed out in passing; it's the reason Chapter 11 has to bolt on an explicit `fix` operator as a new primitive rather than deriving it, and the reason well-typed $\lambda_\to$ programs are *strongly normalizing* (Chapter 12) — they all terminate. You're trading expressive power for a static guarantee.

## Function types

**Book definition (9.1.1).** The set of simple types over `Bool` is generated by:

$$
T ::= \mathsf{Bool} \mid T \to T
$$

with `→` right-associative, so $T_1 \to T_2 \to T_3$ means $T_1 \to (T_2 \to T_3)$ — read it as "a function that takes a $T_1$ and returns a function from $T_2$ to $T_3$," which is exactly currying at the type level. $(\mathsf{Bool}\to\mathsf{Bool})\to(\mathsf{Bool}\to\mathsf{Bool})$ is the type of a function that takes boolean-functions and returns boolean-functions — a higher-order function, typed as such.

**Rust [[Bounded-Quantification#Grounding|grounding]].** This grammar is a recursive `enum`, nothing more:

```rust
#[derive(Clone, PartialEq, Debug)]
enum Type {
    Bool,
    Arrow(Box<Type>, Box<Type>),
}
```

`Type::Arrow(Box::new(Type::Bool), Box::new(Type::Bool))` is `Bool → Bool`. There's no cleverness here — the point is that from Chapter 9 onward, *every* type system in the book is "add one more variant to this enum, add one more pair of typing rules." Keep that pattern in mind; it's the skeleton every later chapter (records, sums, references, polymorphism, kinds) reuses.

## Explicit annotation: why $\lambda x{:}T_1.t$, not $\lambda x.t$

To type an abstraction $\lambda x.t_2$, you need to know the type of $x$ before you can check the body — but nothing in the syntax says what that type is. Pierce's fix, adopted for essentially the rest of the book, is to **annotate the bound variable**: write $\lambda x{:}T_1.\,t_2$. This makes the calculus **explicitly typed**. The alternative — inferring the argument's type from how it's used in the body — is **implicitly typed** (deferred to Chapter 22, ML-style [[Type-Reconstruction|type reconstruction]]). This is a real fork in language design, not a notational nicety: explicitly typed calculi make typechecking a straightforward structural recursion; implicitly typed calculi require solving constraints (unification) to reconstruct the missing annotations.

## The typing relation

Because terms can nest abstractions, you can't get away with a two-place relation $t : T$ (as in Chapter 8) once you introduce variables — you need to track, for every free variable in scope, what type it's assumed to have. That's the **typing context** $\Gamma$: a sequence of variable/type bindings, extended on the right by "comma," with $\emptyset$ (or just the absence of anything on the left of $\vdash$) for the empty context. The full relation is three-place:

$$
\Gamma \vdash t : T
$$

read as "under the assumptions in $\Gamma$, the term $t$ has type $T$." Think of $\Gamma$ as a finite function from variable names to types; $\mathrm{dom}(\Gamma)$ is the set of variables it binds. (Convention: any newly-bound name is required to be fresh with respect to $\Gamma$ — since bound variables can always be renamed, this is never a real restriction, just bookkeeping to keep the proofs clean.)

Three rules generate the relation for the pure calculus (Figure 9-1):

$$
\frac{x{:}T \in \Gamma}{\Gamma \vdash x : T} \quad(\text{T-Var})
\qquad
\frac{\Gamma, x{:}T_1 \vdash t_2 : T_2}{\Gamma \vdash \lambda x{:}T_1.\,t_2 : T_1 \to T_2} \quad(\text{T-Abs})
\qquad
\frac{\Gamma \vdash t_1 : T_{11}\to T_{12} \qquad \Gamma \vdash t_2 : T_{11}}{\Gamma \vdash t_1\,t_2 : T_{12}} \quad(\text{T-App})
$$

- **T-Var**: a variable's type is whatever's currently on record for it in $\Gamma$. No computation, just a lookup.
- **T-Abs**: to type $\lambda x{:}T_1.t_2$ as $T_1 \to T_2$, extend the context with $x{:}T_1$ and check that the *body* $t_2$ has type $T_2$ under that extended context. The premise literally adds one more assumption to the ones already in the conclusion.
- **T-App**: to type $t_1\,t_2$, $t_1$ must be a function $T_{11}\to T_{12}$ and $t_2$'s type must match the domain $T_{11}$ exactly; the result is the codomain $T_{12}$.

The existing rules for `Bool`/`if` (Chapter 8) carry over unchanged except that every judgment now needs the $\Gamma$ threaded through, e.g. T-If becomes $\Gamma \vdash t_1 : \mathsf{Bool}$, $\Gamma \vdash t_2 : T$, $\Gamma \vdash t_3 : T$ implies $\Gamma \vdash \text{if } t_1 \text{ then } t_2 \text{ else } t_3 : T$ — and note $T$ can now be instantiated to a function type, so both branches of a conditional can themselves be functions.

This whole system — types, contexts, and these three rules over the pure lambda-calculus — is what Pierce calls $\lambda_\to$.

**What breaks without the context:** without $\Gamma$, `T-Var` has literally nothing to look up — you cannot type an open term at all, and every abstraction body containing a bound variable becomes untypeable the moment you try to check it in isolation. The context is not bookkeeping; it's the mechanism that lets the "check the body" step in T-Abs make sense.

### Derivations are trees, and typechecking is a tree-shaped algorithm

Just like evaluation derivations in Chapter 3, instances of these rules chain into **derivation trees**. Here is the book's example, showing $\vdash (\lambda x{:}\mathsf{Bool}.\,x)\ \mathsf{true} : \mathsf{Bool}$ in the empty context:

$$
\cfrac{
  \cfrac{
    \cfrac{x{:}\mathsf{Bool} \in x{:}\mathsf{Bool}}{x{:}\mathsf{Bool} \vdash x : \mathsf{Bool}}\ \text{T-Var}
  }{\vdash \lambda x{:}\mathsf{Bool}.\,x : \mathsf{Bool}\to\mathsf{Bool}}\ \text{T-Abs}
  \qquad
  \vdash \mathsf{true} : \mathsf{Bool}\ \ \text{T-True}
}{
  \vdash (\lambda x{:}\mathsf{Bool}.\,x)\ \mathsf{true} : \mathsf{Bool}
}\ \text{T-App}
$$

Crucially, this tree isn't just a proof artifact you draw by hand — its shape *is* the typechecking algorithm. At every node, exactly one rule's conclusion matches the term's top-level syntactic form (an application can only be concluded by T-App, an abstraction only by T-Abs, and so on), so there is never a choice to make about which rule to try. This property — **syntax-directedness** — is what makes typechecking here a simple, terminating structural recursion over the term rather than a search problem. (Contrast this with later systems, e.g. subtyping in Chapter 15, where [[Subtyping#The subsumption rule|the subsumption rule]] T-Sub can apply *anywhere*, breaking syntax-directedness and forcing a real algorithmic redesign in Chapter 16.)

**Rust grounding — the typechecker mirrors the tree exactly:**

```rust
fn typeof_term(ctx: &Vec<(String, Type)>, t: &Term) -> Result<Type, String> {
    match t {
        Term::Var(x) => ctx.iter().rev()
            .find(|(name, _)| name == x)
            .map(|(_, ty)| ty.clone())
            .ok_or_else(|| format!("unbound variable {x}")),          // T-Var
        Term::Abs(x, ty1, body) => {
            let mut ctx2 = ctx.clone();
            ctx2.push((x.clone(), ty1.clone()));
            let ty2 = typeof_term(&ctx2, body)?;
            Ok(Type::Arrow(Box::new(ty1.clone()), Box::new(ty2)))     // T-Abs
        }
        Term::App(t1, t2) => {
            let ty1 = typeof_term(ctx, t1)?;
            let ty2 = typeof_term(ctx, t2)?;
            match ty1 {
                Type::Arrow(t11, t12) if *t11 == ty2 => Ok(*t12),     // T-App
                Type::Arrow(t11, _) => Err(format!("expected {t11:?}, got {ty2:?}")),
                _ => Err("applying a non-function".into()),
            }
        }
        // Term::True | Term::False | Term::If(..) as in Chapter 8, threaded through ctx
        _ => unimplemented!(),
    }
}
```

Every `match` arm is one typing rule; the recursive calls are the premises; the returned `Type` is the conclusion. This is not an analogy — it's literally what Pierce does in the book's own OCaml `typeof` (Chapter 10).

**Lean grounding.** Because this whole judgment is a proof-theoretic object, Lean's kernel gives the most literal possible mirror of it: a typing derivation for $\Gamma \vdash t : T$ *is* an inductive proof term, in exactly the same sense that a Lean term inhabiting a `Prop` is a proof. Modeling it directly:

```lean
inductive Ty where
  | bool : Ty
  | arrow : Ty → Ty → Ty

inductive Term where
  | var   : String → Term
  | abs   : String → Ty → Term → Term
  | app   : Term → Term → Term

inductive HasType : List (String × Ty) → Term → Ty → Prop where
  | tvar : (x, T) ∈ Γ → HasType Γ (.var x) T
  | tabs : HasType ((x, T1) :: Γ) t2 T2 →
           HasType Γ (.abs x T1 t2) (.arrow T1 T2)
  | tapp : HasType Γ t1 (.arrow T11 T12) → HasType Γ t2 T11 →
           HasType Γ (.app t1 t2) T12
```

`HasType` here is not a checker you run — it's a relation, exactly as the book presents it, and a term of type `HasType Γ t T` *is* a derivation tree. Building one by hand for the worked example above is a one-to-one translation of the tree drawn above into `HasType.tapp (HasType.tabs (HasType.tvar ...)) HasType.ttrue`.

## Uniqueness, inversion, and why typechecking here needs no search

Two structural theorems round out §9.3 and matter more than they look:

**9.3.1 Inversion of the typing relation.** This is the converse reading of each rule — instead of "if the premises hold, you may conclude the typing," it says "if this typing holds, the premises *must* have held." E.g.: if $\Gamma \vdash \lambda x{:}T_1.\,t_2 : R$, then necessarily $R = T_1 \to R_2$ for some $R_2$ with $\Gamma, x{:}T_1 \vdash t_2 : R_2$. Inversion is what a typechecker implicitly uses every time it pattern-matches on a term's syntactic form and knows exactly which fields of the resulting type it's allowed to assume.

**9.3.3 Uniqueness of Types.** In a fixed context $\Gamma$, a typable term has *at most one* type, and — because the rules are syntax-directed — exactly one derivation tree deriving it. Terms and their typing derivations are in one-to-one correspondence at this stage. This is a genuinely fragile property: the moment subsumption (T-Sub) is introduced in Chapter 15, it breaks — a single term can then have many valid supertypes, and typechecking algorithms have to compute a *minimal* type rather than *the* type. STLC is the one point in the book where "the type of a term" is an unambiguous, unique thing to ask for.

Two structural lemmas (Permutation, Weakening) and one workhorse lemma close out the properties section:

**9.3.8 Preservation of types under substitution.** If $\Gamma, x{:}S \vdash t : T$ and $\Gamma \vdash s : S$, then $\Gamma \vdash [x \mapsto s]t : T$. This is *the* substitution lemma every safety proof in the rest of the book depends on — it says that plugging a well-typed term into a well-typed hole produces something well-typed, which is exactly what happens at every beta-reduction step (`E-AppAbs`: $(\lambda x{:}T_{11}.t_{12})\ v_2 \to [x \mapsto v_2]t_{12}$). Without it, preservation (below) has no way to get started on the one evaluation rule that actually does something interesting.

## Progress and preservation, specialized to $\lambda_\to$

The vault's [[Type-Safety|Type Safety]] article develops progress and preservation as a general pattern across several chapters (8, 9, 13, 14) — go there for the broader "why does type safety even mean this" treatment. What's specific to this chapter:

- **Canonical Forms (9.3.4)** gets a new clause: a value of type $T_1 \to T_2$ must have the shape $\lambda x{:}T_1.\,t_2$ — abstractions are the *only* values that inhabit function types. (This is what makes E-AppAbs always applicable once both sides of an application are values.)
- **Progress (9.3.5)** needs one real caveat that Chapter 8's version didn't: it only holds for *closed* terms. An open term like $f\ \mathsf{true}$ (with $f$ a free variable) is a normal form — no rule applies — but it's not stuck in the "type error" sense, because it's not a complete program. Progress is a claim about programs you can actually run, and those are always closed.
- **Preservation (9.3.9)** is proved by induction on the typing derivation exactly as in Chapter 8, except the application case now needs Lemma 9.3.8 (substitution) to handle the one new evaluation rule, E-AppAbs.

Together they still deliver Milner's guarantee — a closed, well-typed $\lambda_\to$ term never gets stuck — but the mechanism (canonical forms + substitution) is now doing real work that the type-free Chapter 8 calculus didn't need.

## The Curry-Howard correspondence, briefly

`→` carries two rules with a specific shape: T-Abs is an **introduction** rule (how to build a term of this type), T-App is an **elimination** rule (how to use one). When an introduction form sits directly inside a matching elimination form — a `λ` applied — you get a **redex**, an opportunity to compute. This introduction/elimination pairing recurs for every type constructor in the rest of the book (products, sums, existentials, ...), so it's worth internalizing here.

Pierce flags — without belaboring — that this pairing is not a coincidence: it's the syntactic footprint of the **Curry-Howard correspondence** between type theory and constructive logic:

| Logic | Programming languages |
|---|---|
| proposition $P$ | type $T$ |
| proposition $P \supset Q$ | type $P \to Q$ |
| proposition $P \wedge Q$ | type $P \times Q$ (§11.6) |
| proof of $P$ | term $t$ of type $P$ |
| $P$ is provable | $P$ is inhabited (by some term) |

A well-typed term of type $P \to Q$ *is* a proof that $P$ implies $Q$: a mechanical procedure turning evidence for $P$ into evidence for $Q$. Reduction (running the term) corresponds to proof simplification (cut elimination). This isn't limited to STLC — System F (Ch. 23) corresponds to second-order logic, System $F^\omega$ (Ch. 30) to a higher-order logic. It's the single most important conceptual bridge the book builds, and STLC/$\to$/$\supset$ is the smallest instance of it.

## Erasure and typability

Type annotations play no role in *evaluation* — E-AppAbs's substitution doesn't inspect $T_{11}$ — they only guide typechecking. That observation is made precise by an **erasure function**, stripping annotations back to an untyped term:

$$
\mathrm{erase}(x) = x \qquad
\mathrm{erase}(\lambda x{:}T_1.\,t_2) = \lambda x.\,\mathrm{erase}(t_2) \qquad
\mathrm{erase}(t_1\,t_2) = \mathrm{erase}(t_1)\ \mathrm{erase}(t_2)
$$

Theorem 9.5.2 ("evaluation commutes with erasure") says it doesn't matter whether you evaluate the typed term directly or erase it first and evaluate the untyped residue — same answer either way. This is the formal justification for what every real compiler does: type annotations are load-bearing at compile time only, and get thrown away before the program actually runs.

This motivates the notion of **typability**: an untyped term $m$ is typable in $\lambda_\to$ if some annotated $t$ erases to $m$ and is well-typed. Whether every reasonable untyped term is typable in this sense — and how to *find* the missing annotations automatically — is exactly the type reconstruction problem picked up in full in Chapter 22.

## Curry-style vs. Church-style

Two ways to organize a language definition, and the book is explicit about which one it's using:

- **Curry-style**: define terms, define their runtime behavior *independent of typing*, then use a type system to reject the behaviors you don't like. Semantics is prior to typing — it makes sense to ask "what does this ill-typed term do?" even if you'd never run it. Implicitly-typed presentations are usually Curry-style.
- **Church-style**: typing is prior to semantics. You only ever give meaning to *well-typed* terms — strictly, you evaluate typing *derivations*, not bare terms; ill-typed terms have no defined behavior at all, not even a "stuck" one. Explicitly-typed presentations are usually given Church-style.

Chapter 9's own evaluation relation is defined directly on annotated terms and doesn't care whether the annotations are consistent with a valid derivation — so, strictly, it's closer to Curry-style dressed in explicit-typing clothes, and Pierce flags that this terminological pairing (Church ↔ explicit, Curry ↔ implicit) is common but not a strict rule.

## Reading the rules bidirectionally

The three rules of $\lambda_\to$ split cleanly along a line that becomes explicit machinery later (Chapter 22 and beyond, and in every practical bidirectional elaborator): which rules can *compute* a type from a term, and which need a type handed to them first.

- **T-Var** and **T-App** are naturally **synthesizing** (inference mode, often written $\Gamma \vdash t \Rightarrow T$): given $t_1\,t_2$, you can recursively infer $t_1$'s type, read off its domain/codomain, and check $t_2$ against the domain — no externally-supplied type is needed to get started. T-Var is a pure lookup, the base case of synthesis.
- **T-Abs** is different: given only $\lambda x.\,t_2$ with no annotation, there is no way to synthesize a type — you'd have to guess $T_1$. That's precisely why Pierce's explicit syntax bakes the annotation *into the term* ($\lambda x{:}T_1.\,t_2$): it turns T-Abs from something that would need **checking mode** ($\Gamma \vdash t \Leftarrow T$, i.e. "given a candidate function type, verify the body against its codomain") into something that can still synthesize, only because the annotation supplies exactly the missing piece by construction.

This split — applications and variables synthesize, abstractions fundamentally want to be checked against an expected type — is the seed of full bidirectional typing: a real elaborator (Lean's included) runs exactly this synthesize/check alternation, and the reason lambda literals are usually elaborated in checking mode against an expected function type (rather than requiring the programmer to annotate every one) is that checking mode is what lets you drop the annotation T-Abs otherwise forces on you. Chapter 22's type reconstruction is, in effect, the algorithmic answer to "how far can synthesis alone get without ever needing checking mode."

## Where this leads

$\lambda_\to$ is the load-bearing base every later chapter in the book extends without ever revisiting: base types and derived forms (Ch. 11) just add more type constructors and more T-rules of the same shape; subtyping (Ch. 15) adds one rule (T-Sub) that breaks the syntax-directedness and uniqueness properties proved here, forcing the algorithmic redesign of Ch. 16; polymorphism (System F, Ch. 23) generalizes T-Abs/T-App to the type level; [[Dependent-Types|dependent types]] (Ch. 24, 30) let $T$ itself depend on a term. Every one of those systems is judged by whether it still proves *some* version of progress and preservation, using *some* version of the canonical-forms/substitution machinery introduced right here.

For the standing projects this vault is tracking: the judgment $\Gamma \vdash t : T$ and its three syntax-directed rules are the literal, unabridged template for a checker's core typing function — the Rust `typeof_term` sketch above is not a simplification of what a real verifier does, it *is* what a real verifier's typing core does, before any subtyping, unification, or metavariables are layered on. And the synthesis/checking split identified above is the smallest possible instance of the bidirectional-typing discipline that a metavariable-unification elaborator (in the spirit of Lean's) needs at every node of its term traversal — T-Var/T-App as the always-synthesizing spine, T-Abs as the rule that wants an expected type handed down from its parent.
