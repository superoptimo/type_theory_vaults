# Context-Free Tree Languages

[[book-guidelines|↩ Back to guidelines]]

Regular tree grammars (the previous topic) generate a tree by expanding arity-0 nonterminals — a nonterminal is just a placeholder for "some tree," with no memory of *which* tree it eventually becomes relative to its siblings. That's exactly why they can't express recursion with parameters: there's no way for a nonterminal to say "expand into a tree built out of *this specific argument*, possibly several times, possibly transformed." Context-free tree grammars fix that by giving nonterminals arity — they become functions.

## What breaks without this: real recursive functions

Consider trying to write a grammar for factorial as a term. You want something whose derivation shape mirrors:

$$\mathrm{fact}(x) = \mathbf{if}\ x = 0\ \mathbf{then}\ 1\ \mathbf{else}\ x \times \mathrm{fact}(x-1)$$

A regular tree grammar's nonterminals are arity-0, so a nonterminal like $\mathit{Fact}$ can only ever expand into some fixed tree shape — it has no slot to receive "the current value of $x$" and thread it into both the multiplication and the recursive call. You'd need a different nonterminal for every value of $x$, which is exactly what "not regular" means here — you're describing an unbounded family with no finite grammar.

The book's fix: let nonterminals carry arguments, i.e. take on arities like ordinary function symbols do.

## Context-free tree grammars

A **context-free tree grammar** is $G = (S, N, F, R)$ where the rules now have the shape

$$X(x_1, \dots, x_n) \to t, \qquad t \in T(F \cup N \cup \{x_1,\dots,x_n\})$$

with $X$ a nonterminal of arity $n$ and $x_1,\dots,x_n$ drawn from a reserved set of variables $\mathcal{X}$, disjoint from $F \cup N$. Compare this to a regular tree grammar's rules $A \to f(A_1,\dots,A_n)$: there, the *right-hand side* branches on the terminal's arity; here, the *left-hand side* itself takes arguments, and the right-hand side can mention those arguments anywhere — including inside a recursive call to $X$ itself.

The book's own factorial example, verbatim in spirit:

$$
\begin{aligned}
\mathit{Prog} &\to \mathit{Fact}(\mathit{Nat}) \\
\mathit{Nat} &\to 0 \\
\mathit{Nat} &\to s(\mathit{Nat}) \\
\mathit{Fact}(x) &\to \mathrm{if}(\mathrm{eq}(x,0),\, s(0)) \\
\mathit{Fact}(x) &\to \mathrm{if}(\mathrm{not}(\mathrm{eq}(x,0)),\, \mathrm{times}(x,\, \mathit{Fact}(\mathrm{dec}(x))))
\end{aligned}
$$

$\mathit{Fact}$ is a genuine unary function symbol at the grammar level: its rule mentions $x$ three times, and one of those mentions is itself wrapped in $\mathit{Fact}$ again. This is a recursive program scheme, syntactically.

**Derivation**, generalized from the regular case: $s \to t$ iff there's a rule $X(x_1,\dots,x_n) \to \alpha \in R$, a context $C$, such that $s = C[X(t_1,\dots,t_n)]$ and $t = C[\alpha\{x_1 \leftarrow t_1,\dots,x_n \leftarrow t_n\}]$ — i.e. you find an occurrence of the nonterminal applied to some argument trees, and replace it with the rule's body, substituting the arguments in. A sample run:

$$\mathit{Prog} \to \mathit{Fact}(\mathit{Nat}) \to \mathit{Fact}(0) \to \mathrm{if}(\mathrm{eq}(0,0),\, s(0))$$

$L(G)$ is, as before, the set of ground terms reachable from the axiom. These are **context-free tree languages**, and — mirroring the word case — they sit above regular tree languages in a strict containment:

$$\text{regular} \subsetneq \text{context-free} \subsetneq \text{recursively enumerable}$$

(Recursively-enumerable tree languages, generated by unrestricted tree grammars, are too unconstrained to say anything useful about — the book notes any Turing machine can be simulated by a single-rule term rewrite system, so that class buys you nothing but full undecidability.) Context-free tree languages are closed under union, concatenation, and (Kleene-style) closure, and there's a pushdown-tree-automaton characterization — TATA doesn't develop that machinery here and points to the bibliographic notes instead.

## Evaluation order becomes a real question: IO vs. OI

Here's the section's actual payload. Once a nonterminal is a function that can call itself, *when* you're allowed to expand which occurrence starts to matter — exactly the way it matters for real programs. A rule like $\mathit{Fact}(x) \to \dots \times \mathit{Fact}(\mathrm{dec}(x))$ contains both an argument position ($x$) and a recursive call; a derivation is free, in general, to expand *either* the argument or the nested nonterminal call first. The book names the two disciplined choices:

- **IO (innermost-outermost)**: legal derivations must expand the *innermost* nonterminal occurrences first. This is exactly **call-by-value**: you fully reduce a function's arguments before substituting them into the function body.
- **OI (outermost-innermost)**: legal derivations must expand the *outermost* nonterminal occurrences first. This is exactly **call-by-name**: you substitute the (possibly still-unreduced) argument expression into the body first, and only reduce it later, at each place it's used.

If you've ever cared about the difference between evaluating an argument once versus re-evaluating it every time it's referenced in the body, you already understand IO vs. OI — it's the tree-grammar formalization of exactly that.

### Where OI and IO actually diverge

The divergence needs the nonterminal to *use its argument more than once* in the body — a linear rule (each variable used once) can't tell IO from OI, since there's nothing to duplicate. The book's example makes this concrete. Take:

$$
\begin{aligned}
\mathit{Exp} &\to \mathit{Dup}(\mathit{Nat}) \\
\mathit{Nat} &\to s(\mathit{Nat}) \mid 0 \\
\mathit{Dup}(x) &\to \mathrm{double}(x, x)
\end{aligned}
$$

$\mathit{Dup}$'s rule uses $x$ twice — non-linear. Two derivation disciplines, two different outcomes:

- **OI** (call-by-name: substitute $\mathit{Nat}$ into both argument slots of $\mathrm{double}$ *before* forcing it to a numeral): $\mathit{Exp} \to \mathit{Dup}(\mathit{Nat}) \to \mathrm{double}(\mathit{Nat}, \mathit{Nat}) \to^* \mathrm{double}(s^n(0), s^m(0))$ — the two copies of $\mathit{Nat}$ are expanded *independently*, so they can land on different numerals. $L(\mathit{OI}\text{-}G) = \{\mathrm{double}(s^n(0), s^m(0)) \mid n,m \in \mathbb{N}\}$.
- **IO** (call-by-value: force $\mathit{Nat}$ down to a single concrete numeral *before* duplicating it into $\mathrm{double}$'s two slots): $\mathit{Exp} \to \mathit{Dup}(\mathit{Nat}) \to \mathit{Dup}(s^n(0)) \to \mathrm{double}(s^n(0), s^n(0))$ — one evaluation, copied. $L(\mathit{IO}\text{-}G) = \{\mathrm{double}(s^n(0), s^n(0)) \mid n \in \mathbb{N}\}$.

IO's language is visibly smaller — it can only ever produce *matched* pairs, because there is only ever one evaluation of $\mathit{Nat}$ to copy. This is **Theorem 2.5.3**: $L(\mathit{IO}\text{-}G) \subseteq L(\mathit{OI}\text{-}G) = L(G)$, and the inclusion is strict in general — this example is the strictness witness.

### Why linearity closes the gap

The book flags this as the deep point, and it's worth sitting with: the IO/OI gap exists *only because* a nonterminal's argument variable can occur more than once on the right-hand side. If every rule is **right-linear** (each $x_i$ occurs at most once in $t$), there is nothing to duplicate — substituting the argument once, in one place, obviously commutes with whether you'd reduced it first or not. IO and OI derivations then produce exactly the same trees, and the distinction evaporates.

The book explicitly draws the parallel to Chapter 1: recall that a tree homomorphism's *inverse* image always preserves recognizability, but its *direct* image only does so when the homomorphism is **linear**. Both failures have the identical shape — a construction that duplicates a subtree (a non-linear homomorphism copying a variable's image into multiple positions; a non-linear grammar rule copying an argument into multiple positions) breaks a property (recognizability; IO = OI) that holds unconditionally once duplication is forbidden. Non-linearity is the single recurring villain across this whole book, and here it's the exact same villain wearing an evaluation-order costume.

### Closure properties, and a wrinkle

IO-languages are closed under union and under intersection with regular tree languages — well-behaved so far. Concatenation is not innocent, though: naive concatenation would treat a non-right-linear rule's duplicated constant as free to vary per-occurrence, but IO-derivation semantics says a duplicated argument is evaluated *once* and copied, so concatenation has to be redefined to respect that — "all occurrences of a constant generated by a non-right-linear rule are replaced by the same term." The book's Example 2.5.4 shows the effect: for $L = \mathit{IO}\text{-}G$ with $\mathit{Fct}(x,y) \to f(x,x,y)$ and $M = \{0,1\}$, the language $L\!\cdot\!_2 M$ contains $f(0,0,0), f(0,0,1), f(1,1,0), f(1,1,1)$ but *not* $f(1,0,1)$ or $f(0,1,1)$ — the first two positions, tied to the same duplicated argument, must always agree.

## Grounding: this is literally your evaluator's strategy flag

**Rust.** If you've ever written an interpreter with a `Value` enum and an `eval` function, the IO/OI choice is precisely the choice of *when* you call `eval` on an argument relative to substituting it into the callee body:

```rust
enum Term {
    Var(usize),
    Ctor(String, Vec<Term>),
    Call(String, Vec<Term>), // nonterminal application, arity = args.len()
}

// IO / call-by-value: eval every argument BEFORE substituting into the body.
fn step_io(rules: &Rules, t: &Term) -> Term {
    match t {
        Term::Call(name, args) => {
            let reduced_args: Vec<Term> = args.iter().map(|a| eval_to_normal_form(rules, a)).collect();
            substitute(rules.body_of(name), &reduced_args)
        }
        _ => t.clone(),
    }
}

// OI / call-by-name: substitute the (possibly unevaluated) arguments straight into the body.
fn step_oi(rules: &Rules, t: &Term) -> Term {
    match t {
        Term::Call(name, args) => substitute(rules.body_of(name), args), // no eval_to_normal_form here
        _ => t.clone(),
    }
}
```

`step_io` evaluates each argument to a normal form exactly once, then `substitute` copies that *single already-reduced* term into every occurrence of the parameter — which is exactly why IO can only ever produce matched duplicates, mechanically. `step_oi` copies the raw (possibly still-`Call`-headed) argument term into every occurrence, and each copy goes on to be reduced independently later — which is exactly why OI can produce mismatched pairs. The Rust type signatures don't change between the two; only *when* `eval_to_normal_form` gets called relative to `substitute` changes. That's the whole theorem, in code.

**Python**, as a five-line illustration of the same fork, for `Dup(x) -> double(x, x)` applied to a lazy vs. eager `Nat` generator:

```python
def cbv_dup(nat_thunk):        # IO: force once, copy the result
    n = nat_thunk()             # evaluate to a concrete numeral, once
    return ("double", n, n)     # both slots are literally the same value

def cbn_dup(nat_thunk):         # OI: copy the thunk, force independently later
    return ("double", nat_thunk, nat_thunk)  # each slot may resolve differently
```

**Lean.** Lean's kernel is a call-by-name-flavored reducer at its core (definitional unfolding proceeds lazily, forcing values only when a reduction rule needs to pattern-match on the head), so Lean's `whnf` (weak head normal form) machinery is a live example of an OI-flavored evaluation discipline — a term is unfolded outward-in only as far as is needed to expose the next matchable head, not forced all the way down eagerly. The gap between IO and OI in this book is structurally the same gap Lean's elaborator has to be careful about when deciding *how much* to unfold a term before comparing it against another for definitional equality.

## Where this leads

This is a short section — the book itself treats it as a brief detour past regular tree languages ("we discuss only IO and OI grammars and refer the reader to the bibliographic notes for more") rather than a fully developed theory, and this article matches that proportion rather than padding it.

Structurally, it sits directly above regular tree grammars (the previous topic): same grammar shape, generalized by giving nonterminals arity, which is exactly what buys genuine recursion at the cost of losing the automaton-based decidability toolkit regular tree languages enjoy.

For the compiler/elaborator project: this section is a clean, self-contained miniature of the eager-vs-lazy evaluation-order distinction that will resurface at full scale in your bidirectional typing and operational-semantics work — deciding whether to normalize a term before or after substituting it into a typing judgment is the identical fork under a different name. It's also a preview of the non-linearity theme that governs Miller pattern unification: a duplicated variable occurrence is exactly what pattern unification's "distinct bound variables" restriction is designed to keep from happening in an argument list, for the same underlying reason IO/OI diverge only under non-linearity — duplication is where naive syntactic reasoning about substitution stops being sound.
